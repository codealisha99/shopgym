Browser agents, graded by the database.

ShopGym is a self-hosted shop and an environment that lets a browser agent act on it. Each of its 27 tasks is checked against the database and the final answer, so a confident transcript cannot pass.

The checker compares two database states

The hard part of browser-agent evaluation is not the page. It is deciding whether the agent did the job without also doing something else. A transcript can claim success that the store never recorded, and an answer can be right by luck.

Each checker compares a snapshot taken after task setup with the live database at the end, then checks the answer. assert_only fails any row that changed outside the task's allowance. Cancelling order 1043 instead of 1042 fails, even if 1042 was cancelled too.

Expected values come from the snapshot, using the same search query the storefront uses, so answers are never hard-coded. Answer matching is tolerant on purpose: "3", "three" and "3 of 12" all count as 3, while "not shipped" never counts as shipped.

The task file: an instruction, a checker and its parameters.

- id: cancel-order-1042
  tier: medium
  start_url: /account/orders
  setup: login_as
  setup_params: {email: ada@shop.test}
  instruction: "Cancel order #1042. Do not change any other order."
  checker: cancel_order
  params: {number: 1042}

The checker, from tasks/checkers.py.

@checker("cancel_order")
def cancel_order(ctx, number, **_):
    row = _rows(_ro(ctx.final), "orders").get(number)
    if row is None or row["status"] != "cancelled":
        return Verdict(False, f"order {number} is {row and row['status']}, expected cancelled")
    return assert_only(ctx, {"orders": {number}})

How the parts fit

The shop runs once. Each episode copies its own database, and a cookie routes the browser to that copy, so parallel episodes cannot see each other's carts, orders or admin edits.

Where to look in the code

Five files hold the hard parts. Each link goes to the file on GitHub.

  1. tasks/checkers.pyThe checkers and assert_only. A row changed outside the allowance fails the task, even when the right row also changed.
  2. env/observe.pyThe DOM walker that tags interactive elements e1, e2, ... in document order. It also records each element's box, which the replay uses to highlight the target.
  3. tasks/answers.pyTolerant answer matching. "3", "three" and "3 of 12" all count as 3. "not shipped" never counts as shipped.
  4. env/episodes.pyOne seeded database copy per episode, routed by the sg_episode cookie, so parallel episodes cannot see each other.
  5. agents/oracle.pyThe scripted oracle. It finds elements by role and name, the way a user would, and proves each task can be finished through the UI.

Run it

The keyless demo needs Python 3.12 and uv. It boots the shop on port 4200, runs the three agents over all tasks, and writes runs/demo/viewer.html, one self-contained file.

A real model is not part of the demo. The LLM agent takes an Anthropic key, or any OpenAI-compatible server. Its providers are covered by tests with a scripted provider. No live model has been called from this project.

make install     # uv sync + Chromium for Playwright
make demo        # oracle + noop + random, all 27 tasks, headless

make test        # all tests, browser tests included
make test-fast   # everything except the browser tests

uv run shopgym serve            # the shop on http://127.0.0.1:4200
uv run shopgym tasks            # list tasks
uv run shopgym report runs/demo
uv run shopgym view runs/demo --out viewer.html

Limitations

These are the gaps that matter for judging the work, stated plainly. There is no live demo: the shop runs locally with one command.

  • No live model run. The LLM agent and its providers are tested with a scripted provider only. The first real run should be a few tasks, checked by hand.
  • The oracle is privileged. It may read the seed database to find an answer. It proves solvability, not agent skill.
  • No coordinate grounding in any task. Pixel clicks exist, and only the random baseline uses them.
  • Narrow shop. English only, one currency, UK addresses, and test cards only.
  • 27 tasks. Adding one means a task entry, a checker if none fits, and an oracle. The tests catch a missing piece.
  • Back-button and multi-tab recovery are lightly exercised. No task depends on them.
