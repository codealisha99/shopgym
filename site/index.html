Did the order really get cancelled? ShopGym checks the database, not the transcript.

ShopGym is a self-hosted shop with an admin panel, and an environment that lets a browser agent act on it through screenshots and a text view of the page. Each of its 27 tasks has a checker that diffs database snapshots and the agent's final answer, and fails any side effect the task did not ask for.

Run the store locally Read the source

No live demo is running yet. The shop runs locally with one command, and this page shows real output from that run.

A checker is a function over two database states

The hard problem in browser-agent evaluation is not the page. It is deciding whether the agent did the job without also doing something else. A transcript can claim success that the store never recorded, and an answer can be right by luck.

Each ShopGym checker compares a snapshot taken after task setup with the live database at the end, and then checks the answer. assert_only fails any row that changed outside the task's allowance. Cancelling order 1043 instead of 1042 fails, even if 1042 was cancelled too.

Expected values are computed from the snapshot, using the same search query the storefront uses, so answers are never hard-coded. Answer matching is tolerant on purpose. "3", "three" and "3 of 12" all count as 3, while "not shipped" never counts as shipped, and each rule has its own tests.

The task file: an instruction, a checker and its parameters.

- id: cancel-order-1042
  tier: medium
  start_url: /account/orders
  setup: login_as
  setup_params: {email: ada@shop.test}
  instruction: "Cancel order #1042. Do not change any other order."
  checker: cancel_order
  params: {number: 1042}

The checker, from tasks/checkers.py.

@checker("cancel_order")
def cancel_order(ctx, number, **_):
    row = _rows(_ro(ctx.final), "orders").get(number)
    if row is None or row["status"] != "cancelled":
        return Verdict(False, f"order {number} is {row and row['status']}, expected cancelled")
    return assert_only(ctx, {"orders": {number}})

How the parts fit

The shop runs once. Each episode copies its own database, and a cookie routes the browser to that copy, so parallel episodes cannot see each other's carts, orders or admin edits.

Run it

The keyless demo needs Python 3.12 and uv. It boots the shop on port 4200, runs the three agents over all tasks, and writes runs/demo/viewer.html, which is one self-contained file.

A real model is not part of the demo. The LLM agent takes an Anthropic key, or any OpenAI-compatible server. Its providers are covered by tests with a scripted provider, and no live model has been called from this project.

make install     # uv sync + Chromium for Playwright
make demo        # oracle + noop + random, all 27 tasks, headless

make test        # all tests, browser tests included
make test-fast   # everything except the browser tests

uv run shopgym serve            # the shop on http://127.0.0.1:4200
uv run shopgym tasks            # list tasks
uv run shopgym report runs/demo
uv run shopgym view runs/demo --out viewer.html

Limitations

These are the gaps that matter for judging the work, stated plainly.

  • No live model run. The LLM agent and its providers are tested with a scripted provider only. The first real run should be a few tasks, checked by hand.
  • The oracle is privileged. It may read the seed database to find an answer. It proves solvability, not agent skill.
  • No coordinate grounding in any task. Pixel clicks exist, and only the random baseline uses them.
  • Narrow shop. English only, one currency, UK addresses, and test cards only.
  • 27 tasks. Adding one means a task entry, a checker if none fits, and an oracle. The tests catch a missing piece.
  • Back-button and multi-tab recovery are lightly exercised. No task depends on them.
